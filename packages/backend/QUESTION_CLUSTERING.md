# 代表项计算

ChromaDB 单集合、多集合和文本投影支持代表项计算。文件已有向量时，同时指定 `--vector` 和 `--text`。Python 接口使用 `compute_vector_projection(..., text="文本列名")`。

在散点图上色字段中选择 `representative_item`。如有同名原始列，生成列使用数字后缀，例如 `representative_item_1`。未达到相似度阈值的条目为 `null`，使用空值颜色。所有原始行都参与 UMAP。已有 SQL、配置和分享链接中引用旧生成列 `representative_question` 的地方，请改用新列名。

## 多集合自动刷新

服务端 DuckDB 和浏览器 WASM 模式下，打开集合页面后，后端每 15 秒检查一次条目数。条数变化时立即核对 ID；条数相同时每 60 秒核对一次 ID，以发现等量替换。多个页面共用检查。带本地快照启动时，集合 UUID 和 ID 都一致就直接恢复结果。只增加 ID 时按 ID 分批获取新增记录，每批最多 1,000 条。

旧 ID 消失、集合被重建、增量读取无法对齐或本地快照不可用时，会重新读取完整记录。默认同一个 ID 的内容不变；若已知有人原地更新了正文、元数据或向量，可在集合页点击「全量同步」。全量核对发现只有元数据变化时复用投影和代表项，只有正文变化时复用投影；没有变化时继续使用当前版本。刷新失败时页面保留上次成功的版本，打开的集合页会继续检查。

多集合默认启用增量 UMAP。全量拟合的基线达到 100 条后可增量投影。累计新增量以该基线为准，超过 `--incremental-threshold`（默认 20%）时重建 UMAP 和代表项。增量更新只将新条目归到已有代表项。重复文本沿用已有标签，新文本以其首次出现的向量计算归属。删除条目、修改旧向量和增量投影失败也会触发重建。旧文本或聚类参数变化时会重新计算代表项。使用 `--no-incremental` 可选用全量模式。

对于 cosine 或 euclidean 的小批追加（最多 32 条，且总行数 × 新增条数 × 向量维度不超过 20 亿），旧点之间的近邻关系从缓存恢复，只计算涉及新点的距离。其他情况沿用全量近邻计算。达到重新拟合的阈值时，仍可使用本地旧向量和新读取的向量重建。

## 全量算法

1. ChromaDB 单次读取文档、元数据和向量，并按 ID 排序。文件保持输入行顺序。单响应避免分页和分别读取时的错配，数据库级事务快照保证取决于 ChromaDB 服务端。
2. 向量转换为 float32 并 L2 归一化。文本按原值去重并保留频次，同文本使用首次出现的向量。
3. 按频次降序处理，相同频次按首次出现排序。以 0.97 相似度贪心合并尚未分配的文本。
4. 候选代表按余弦相似度 ≥ 0.73 覆盖合并组，每轮选择新增覆盖得分最高者，得分为 `0.4 × 新增不同文本数/全部不同文本数 + 0.6 × 新增条目数/全部条目数`。平局按原始顺序选择，同时达到 80% 和 90.1% 后停止。
5. 对每个不同文本寻找最近代表，以 0.73 阈值判定覆盖后展开到原始行。日志分别输出合并阶段和最终覆盖率，最终覆盖率低于目标时记录警告。

缺失文本的条目记为未覆盖。零向量和非有限向量会报错。参数通过 `packages/backend/.env.example` 中的 `QUESTION_CLUSTER_*` 环境变量配置，修改后重启后端。提高 `SIMILARITY_THRESHOLD` 会收紧归类条件。

## 缓存

应用缓存的 `projections` 目录保存全量代表项结果 `question-clusters-<SHA256>.json`，键包含顺序、原始 float32 向量、文本、算法版本和聚类配置。多集合用 `collection_*.sqlite3` 保存原始行、向量指纹、投影、近邻和代表项。追加时只写入新增原始行；UMAP 模型只在重新拟合时保存，重启后第一次增量投影时才加载。旧格式升级需要一次全量读取。多集合的 Parquet 也按发布版本按需生成一次，供下载和 ZIP 导出复用。

全量代表项计算的额外工作内存为 O(ND + N)，精确相似度计算仍有二次时间成本。增量归属的相似度计算规模取决于新增文本数和已有代表项数。

在仓库根目录运行验证：

```powershell
.venv/Scripts/python.exe -m unittest discover -s packages/backend/tests -v
```

在安装 `psutil` 的开发环境中，可用 50,000 条、384 维合成向量复现加载基准。使用一个新的缓存目录，依次运行三次；每次使用独立的 Python 进程。测试使用真实 UMAP 和本地 SQLite，模拟 Chroma 的读取响应。输出包含各阶段耗时、进程峰值内存、ID 和完整记录的读取量，以及全量近邻计算的次数。向量数据量按 float32 计，不含 HTTP 和 JSON 编码开销。

```powershell
$atlasBench = '.venv/atlas-sync-benchmark'
foreach ($atlasPhase in @('cold', 'warm', 'append')) {
  .venv/Scripts/python.exe packages/backend/tests/benchmark_collection_sync.py $atlasPhase --cache-dir $atlasBench
  if ($LASTEXITCODE -ne 0) { break }
}
```

一次 Windows 本地运行的结果（四个 Numba 线程，内存为整个 Python 进程的峰值）：

| 场景 | 只读 ID | 完整记录 | 读取 / 准备 / 写缓存（秒） | 总耗时（秒） | 峰值内存（MiB） |
| --- | ---: | ---: | --- | ---: | ---: |
| 首次加载 | 0 | 50,000 | 0.019 / 30.760 / 18.903 | 49.682 | 1,661 |
| 带缓存重启 | 50,000 | 0 | 0.224 / 0.933 / 0 | 1.160 | 359 |
| 重启后首次追加 | 100,020 | 10 | 0.270 / 12.042 / 0.042 | 12.385 | 1,058 |

追加阶段的 ID 数包含读取前后的两次核对。完整记录中的向量从 76,800,000 字节降到 15,360 字节，且这次追加没有重算全量近邻。首次追加的准备时间包含从磁盘恢复 UMAP 模型和投影新增点。
